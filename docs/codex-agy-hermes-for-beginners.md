# Codex、Antigravity CLI 與 Hermes：把訂閱用到極致，API 成本斷崖式下降

你有沒有遇過這種情況？

明明已經花錢訂閱了好幾個 AI，平常卻只用其中一個；另一個訂閱放著沒用，真正做大量工作的時候，反而一直消耗 API key，月底看到帳單才發現花費很高。

我就是因為這個原因，開始研究怎麼把手上的 AI 訂閱真正用起來。

這篇不談複雜理論，直接用情境說明：怎麼讓主要 AI 平常工作，其他訂閱在需要時接手，並且減少 API key 的消耗。

## 我的痛點：不是不想付錢，而是 API 帳單一直增加

我本身是 AI 重度使用者，會長時間讓 AI 幫忙寫程式、整理資料、研究問題和反覆測試。

一開始最直接的做法，就是把工作全部丟給 API。剛開始覺得每次只花一點點，沒有什麼；但使用時間一長，請求數和 Tokens 不斷累積，月底看到帳單時，才發現這不是偶爾用用的費用，而是一筆持續增加的支出。

更讓人不舒服的是：我其實已經付費訂閱了其他 AI，卻沒有把那些訂閱額度用起來。

也就是說，一邊讓 API key 持續扣錢，一邊讓已經付費的訂閱閒置。

這才是我真正想解決的問題：**不是再買更多服務，而是把已經付費的服務用到極致。**

![API 帳單與使用量痛點](https://raw.githubusercontent.com/j0935586110-lgtm/tw-ai-forum/main/docs/assets/deepseek-bill-pain-point.jpg)

## 先看結果：API key 使用量明顯下降

在開始使用訂閱模型分擔工作後，我回頭查看 DeepSeek API key 的使用量。

從圖表可以看到，9 月 7 日到 9 月 26 日的使用量比較高；9 月 27 日之後，使用量突然下降，後面只剩少量波動。

![DeepSeek API 使用量驗證](https://raw.githubusercontent.com/j0935586110-lgtm/tw-ai-forum/main/docs/assets/deepseek-usage-after.jpg)

當時儀表板顯示：

- 消費金額：**399.77 USD**
- API 請求：**147,039 次**
- Tokens：**12,353,689,161**

這張圖不能單獨證明每一筆下降都只由訂閱模型造成，但它很清楚地呈現一個結果：把部分工作交給已經付費的訂閱後，原本大量消耗 API key 的曲線明顯降低。

這就是我想達成的事情：**不要讓已經付費的訂閱閒置，同時減少不必要的 API 支出。**

## 用一個簡單情境來理解

假設你每天都要請 AI 做很多事：

- 寫程式
- 修改檔案
- 整理資料
- 研究資料
- 反覆測試
- 檢查另一個 AI 的答案

如果所有工作都丟給同一個 API key，使用量很快就會增加。

但你手上可能已經有：

- OpenAI Codex 訂閱
- Google Antigravity CLI 訂閱
- Claude 或 Gemini 可用的訂閱額度

問題是：這些服務通常各自獨立。你必須自己切換、自己記得哪個額度還沒用完，也很難讓它們互相接手。

所以我加入一個「工作管理員」來安排工作。

## 三個角色怎麼分工？

把它想成一間公司：

### Codex：第一位主要員工

平常的問題先交給 Codex。

例如你說：「幫我整理這份資料，然後修改程式。」通常先由 Codex 處理。

### Antigravity CLI：第二組員工

Antigravity CLI 是另一個 AI 服務入口，可以使用 Gemini 或 Claude。

它不是每次都和 Codex 同時工作，而是在以下情況接手：

- 主要模型暫時不能用
- 主要服務發生錯誤
- 請求太多受到限制
- 你想把工作分給另一個訂閱
- 你想用第二個模型交叉檢查

### Hermes：櫃台主管

Hermes 不一定是回答問題的模型，它比較像櫃台主管：

1. 先接收你的要求。
2. 先交給主要模型。
3. 主要模型失敗時，再交給備援模型。
4. 統一管理檔案和其他工作工具。

你只要跟 Hermes 說話，不需要每次自己打開不同服務、複製內容、再貼回來。

## 實際的工作順序

最簡單可以想成這樣：

```text
第一順位：OpenAI Codex
第二順位：Antigravity CLI + Gemini
第三順位：Antigravity CLI + Claude
```

平常由 Codex 工作；如果它暫時失敗，就換 Gemini；Gemini 也不能用，再換 Claude。

這樣做的重點不是「同一題問三次」，而是讓不同訂閱在需要時都能派上用場。

## 為什麼這樣可以省 API key？

原本的做法可能是：

```text
所有工作 → DeepSeek API key
```

改成訂閱優先後，變成：

```text
一般工作 → Codex 訂閱
需要備援 → Antigravity CLI 訂閱
真的需要時 → API key
```

API key 不一定完全不使用，但可以從「主要工作引擎」變成「備援或特殊用途」。

這就是我說的「把訂閱使用到極致」：不是再買更多服務，而是先把已經付費的額度用好。

## 新手最容易搞錯的地方

### 1. 不是把名稱填進去就完成

你不能只在設定裡寫上 `Antigravity CLI`，就期待系統自動知道怎麼呼叫它。

不同服務需要不同的連接方式。要先確認 provider、登入狀態和模型名稱都能單獨運作，再測試自動備援。

### 2. 有回覆不代表真的完成工作

AI 回答一句「好了」，不代表它真的完成了。

比較可靠的測試方式是請它：

1. 建立一個測試檔案。
2. 把指定內容寫進去。
3. 再讀回檔案。
4. 確認內容真的正確。

### 3. 服務錯誤不一定是額度用完

看到錯誤時，不要馬上認定是額度沒了。

可能的原因包括：

- 網路暫時不通
- 服務端暫時故障
- 請求太快，被限流
- 模型名稱不存在
- 登入狀態失效
- 真的用完額度

要先看錯誤類型，再決定是否切換備援。

### 4. 不要用一次測試就下結論

有時候第一次很快，第二次卻很慢。

所以我會測量完整等待時間，而不只看 AI 自己回報的思考時間。完整時間還可能包含啟動程式、登入、網路重試和關閉背景工作。

## 目前的限制

Gemini 和 Claude 都已透過 Antigravity CLI 單獨測試成功，備援順序也已設定。

但我沒有故意把訂閱額度全部用完，因為那會真的消耗額度。因此目前嚴謹的說法是：

> 已驗證模型可以使用、備援路由可以設定、quota 類錯誤可以分類；但「額度真正用完後自動切換」仍需要真實情境的完整驗證。

## 想自己試，可以照這個順序

1. 先確認主要模型能正常回答。
2. 單獨測試 Antigravity CLI 的 Gemini。
3. 單獨測試 Antigravity CLI 的 Claude。
4. 再設定自動備援。
5. 記錄每次實際使用的模型、錯誤和等待時間。
6. 修改正式設定前先備份，出問題可以還原。
